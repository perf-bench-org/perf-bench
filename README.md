# perf-bench — нагрузочный стенд для vLLM

Генератор нагрузки (JMeter DSL) и генератор Benchmark Report для закрытого контура.
Единственный результат, покидающий контур, — текстовый `report.txt`.

Проектные документы: [ARCHITECTURE.md](ARCHITECTURE.md), [IMPLEMENTATION.md](IMPLEMENTATION.md),
[metrics-storage-stage.md](metrics-storage-stage.md).

## Развёртывание

Порядок обязателен: слой сбора метрик поднимается и проверяется **до** первого прогона и дальше
работает непрерывно. `depends_on` между compose-проектами не работает.

```bash
cd metrics-storage/
docker compose up -d
```

Сеть `loadtest-net` создаётся этим стеком, остальные подключают её как external.

### Где живёт модель

Модель **не в `loadtest-net`**: она на том же хосте — вне докера либо в своей docker-сети с
опубликованным портом. До неё ходят двое: контейнер `loadtest` во время прогона и контейнер
`vmagent` непрерывно.

Оба видят её по имени `vllm` благодаря одной строке в каждом compose-файле:

```yaml
extra_hosts:
  - "vllm:host-gateway"
```

`host-gateway` — штатный механизм Docker (20.10+): имя резолвится в адрес шлюза хоста. Поэтому
при переезде модели правится порт, а не топология.

**Адрес задаётся ровно в одном месте — `VLLM_HOST` и `VLLM_PORT` в корневом `.env`.** Оттуда его
берут оба compose-проекта: тест получает `LT_TARGET_URL` и `LT_VLLM_BASEURL`, а vmagent
разворачивает `%{VLLM_HOST}:%{VLLM_PORT}` в своём scrape-конфиге. Разойтись они больше не могут.

Где развёрнута модель — стенду безразлично, пока она на этом же хосте. Проверенная матрица:

| Где модель | `VLLM_HOST` | Работает |
|---|---|---|
| Вне докера, слушает `0.0.0.0` | `vllm` | да |
| В докере, порт опубликован на `0.0.0.0` | `vllm` | да |
| В докере, подключена к `loadtest-net` | имя контейнера | да |
| В докере, порт опубликован на `127.0.0.1` | — | **нет**, недостижимо из контейнера |

Значение `vllm` резолвится в шлюз хоста через `extra_hosts`. Если модель переехала в `loadtest-net`,
`VLLM_HOST` меняется на имя её контейнера, и запись `extra_hosts` просто перестаёт использоваться —
удалять её не нужно. **Оставлять при этом имя `vllm` нельзя**: `extra_hosts` попадает в
`/etc/hosts` контейнера и перебивает docker DNS, из-за чего контейнер с таким именем в общей сети
становится недоступен.

Следствие, о котором надо знать: `target.url` и `vllm.baseUrl` в `config/test.properties` при
запуске через compose **не действуют** — `LT_`-переменная сильнее файла. Значения там оставлены
как документация формата и как дефолт для запуска jar'а напрямую.

Внутри контейнера `127.0.0.1` — это сам контейнер, а не хост. Адрес модели никогда не бывает
loopback'ом, даже если с хоста она отвечает именно по нему.

Два требования к модели:

- **слушать не только loopback** — для vLLM это `--host 0.0.0.0`. При `--host 127.0.0.1` изнутри
  контейнера её не видно ничем, кроме `network_mode: host`;
- **не быть закрытой firewall'ом хоста** от подсети docker-моста (обычно `172.17.0.0/16`). На
  хосте с firewalld/ufw это единственное, что придётся разрешить явно.

Проверить, куда именно смотрит скрейпер, можно не запуская прогон:

```bash
docker exec vmagent wget -qO- http://127.0.0.1:8429/api/v1/targets
```

Рассинхрон адресов между тестом и скрейпером ловит `Preflight`: он проверяет, что серии `vllm:*`
реально доехали до хранилища, и падает за секунды, а не после сорока минут прогона.

Если модель когда-нибудь переедет **в** `loadtest-net` под именем `vllm`, строки `extra_hosts`
надо убрать: запись попадает в `/etc/hosts` контейнера и перебивает docker DNS.

Проверка слоя после деплоя:

```bash
curl -s 'http://127.0.0.1:8428/api/v1/query?query=vllm:num_requests_running'
```

Непустой `result` — слой рабочий. Более полную проверку делает `Preflight` внутри самого теста.

Останавливать слой между прогонами нельзя: разрывы в рядах сделают невозможным пересчёт отчётов
за прошедшие окна.

## Сборка

Сборка идёт внутри контура, зависимости берутся из зеркала Maven:

```bash
MAVEN_MIRROR_URL=https://nexus.example/repository/maven-public docker compose build loadtest
```

Без `MAVEN_MIRROR_URL` сборка пойдёт напрямую с Maven Central — так собирают снаружи контура.

## Запуск

```bash
docker compose run --rm -e LT_RUN_ID=confirm-180 loadtest
```

```bash
docker compose run --rm -e LT_MODE=step -e LT_RUN_ID=step-search loadtest
```

```bash
docker compose run --rm -e LT_MODE=report -e LT_RUN_ID=confirm-180 loadtest
```

Третья команда пересчитывает отчёт по уже собранным данным, не подавая нагрузку: нужна, когда
правятся пороги штрафов. Исходный `report.txt` не перезаписывается, новый пишется рядом как
`report.recalc-N.txt`.

Переопределение любого параметра конфигурации — переменной окружения `LT_` + ключ в верхнем
регистре с точками, заменёнными на подчёркивания: `LT_MODE`, `LT_FLAT_RPM`, `LT_RUN_ID`,
`LT_SCORING_E2ESLASEC`. Опечатка в имени `LT_`-переменной роняет запуск, а не игнорируется молча.

## Артефакты прогона

`./results/<run_id>/`:

| Файл | Назначение |
|---|---|
| `report.txt` | **основной результат** — Benchmark Report с итоговой оценкой |
| `results.jtl` | сырые результаты без тел ответов; источник клиентских метрик |
| `run.meta.properties` | границы окон удержания, целевые RPM, имена метрик, модель, версия vLLM |
| `config.snapshot.properties` | эффективная конфигурация |
| `jmeter.log` | лог движка |

Каталог с уже использованным `run.id` не перезаписывается — повторный запуск падает на старте.
Исключение: если прогон упал до подачи нагрузки (конфигурация, датасет, preflight), каталог
удаляется — данных в нём нет, и повтор с тем же `LT_RUN_ID` не должен упираться в защиту.

## Что правится и где

| Что | Где |
|---|---|
| Адрес модели | `VLLM_HOST`, `VLLM_PORT` в корневом `.env` — одна точка на тест и скрейпер |
| Профиль, целевой RPM, порог SLA | `config/test.properties` либо `LT_*` |
| Пороги штрафов | константы `Scoring` |
| Параметры тела запроса (`max_tokens`, `temperature`, …) | константы `RequestBody` |
| Имена метрик vLLM | `VllmMetrics.CANDIDATES` |
| Ожидаемая длительность итерации и такт потока | `Threads.ITERATION_SEC`, `Threads.SAFETY` |
| Подокно усреднения p95 и производных | `VllmMetrics.SUBWINDOW_SEC` |
| Интервал скрейпа | `metrics-storage/vmagent-config.yml` **и** `Report.SCRAPE_INTERVAL_SEC` |

Изменение чего-либо из правой половины таблицы требует пересборки образа.

### Имя модели

`RequestBody.MODEL` пуст: preflight берёт имя из `/v1/models` vLLM. Если vLLM отдаёт несколько
моделей, preflight падает — выбирать за оператора нельзя. Чтобы зафиксировать имя жёстко,
впишите его в константу.

### `max_tokens` и `ITERATION_SEC`

`RequestBody.MAX_TOKENS` (1024) вместе с `ignore_eos` определяет длительность итерации, а
`Threads.ITERATION_SEC` (300 с) — то, из чего считается такт потока. Эти две величины должны быть
согласованы: после первых прогонов сверьте фактический `E2E Latency Avg` в отчёте с
`ITERATION_SEC` и поправьте константу. Если ответы стабильно медленнее такта (375 с), поднимать
надо `SAFETY`, а не число потоков напрямую — оно не задаётся.

## Как устроен генератор

Штатная JMeter **Thread Group** плюс **Constant Throughput Timer** — никаких плагинных групп
потоков и плагинных таймеров. Проверяется тестом по сохранённому JMX, а не по сигнатурам DSL.

```
threads = ceil(RPM / 60 x ITERATION_SEC x SAFETY)      # 180 RPM -> 1125 потоков
такт    = threads x 60 / RPM = ITERATION_SEC x SAFETY  # 375 с
таймер  = RPM / threads                                # 0.16 запроса в минуту на поток
```

Таймер выдерживает такт одного потока; при `threads` потоках это даёт ровно целевой RPM.

**Такт — это максимальное время ответа, при котором целевой RPM ещё достижим.** Ответ быстрее
такта не мешает; медленнее — генератор физически не успевает, и фактический RPM проседает.
Отсюда правило согласования: `scoring.e2eSlaSec` должен быть **ниже** такта, иначе появится зона,
где ответ формально укладывается в SLA, а RPM уже недобирается. Конфигурация, нарушающая это
правило, даёт предупреждение при старте.

### Почему режим «this thread only», а не «all active threads»

Обе альтернативы дают неверные цифры, и обе — молча.

**Разделяемые режимы («shared») при длинных запросах перестают работать вовсе.** Таймер считает
момент следующего запроса от момента последнего вызова *этого же потока*. За 300 с, пока идёт
запрос, отметка протухает, расчётный момент оказывается в прошлом, и таймер возвращает нулевую
паузу. Темп тогда определяется не целевым RPM, а числом потоков — прогон идёт на `SAFETY`
(четверть) быстрее заказанного.

**Режимы «all active threads…» считают паузу от числа живых потоков**, а оно растёт всё время
разгона. Такт плывёт вместе с ним, потоки, стартовавшие раньше, получают более короткие паузы, и
переходный процесс выходит за конец разгона — прямо в начало окна измерения.

Режим «на поток» даёт постоянный такт с первой секунды.

### Почему разгон кратен такту

Constant Throughput Timer выпускает **первый запрос каждого потока без задержки** — это его
штатное поведение, а не настройка. Дальше поток повторяется строго через такт. Моменты запросов
поэтому образуют волны: потоки, стартовавшие за время разгона `R`, повторяются через такт `P`,
ещё через `P` и так далее.

При `R < P` волны не смыкаются: во время разгона темп равен `N/R` — выше целевого, — а между
концом разгона и первой волной повторов образуется **провал длиной `P − R` внутри окна
измерения**. На профиле из документов (разгон 300 с, такт 375 с) это 75 секунд без единого
запроса в начале удержания: −4 % throughput и штраф за недобор RPM на ровном месте.

Ровно при кратности волны укладываются встык и темп постоянен с первой секунды. Поэтому заданный
в профиле разгон трактуется как **минимальный** и поднимается до ближайшего кратного такту;
о каждой такой правке стенд сообщает при старте. Нарастает за время разгона не частота
поступления, а загрузка сервера — она выходит на установившуюся за время одного ответа.

### Ступени

Каждая ступень — отдельная группа потоков со своим числом потоков, своим разгоном и своим
таймером. Ступени расставлены штатным планировщиком JMeter: группа ступени i стартует с
задержкой, равной сумме длительностей предыдущих ступеней, и живёт ровно `ramp + hold`. Пауз
между ступенями нет, частота поступления просто переключается с одного значения на другое.

Движок создаёт потоки всех групп сразу на старте прогона, даже тех, что ещё ждут своей очереди.
Для профиля из документов это 5625 потоков; ждущие потоки спят и ресурсов не потребляют, но
размер генератора считать надо по сумме, а не по максимальной ступени. Отчёт печатает её как
`Threads (total)`.

## Ограничения, которые важно понимать при чтении отчёта

- **`Threads (peak observed)`** в отчёте отвечает на вопрос, из-за чего недобор RPM: пик, равный
  числу потоков ступени, означает, что заняты все потоки и упёрлись мы в генератор, а не в
  модель — о сервере такая ступень ничего не говорит.
- **`p95 (max)`** — худший наблюдённый участок прогона, а не максимум отдельных наблюдений:
  последнего в бакетах гистограммы не существует. Величина зависит от подокна, оно печатается
  рядом. Единственный настоящий максимум в отчёте — `E2E Latency Max`.
- **`Queue Max` и `KV Cache Max`** ограничены интервалом скрейпа: всплеск короче 5 с в данных
  физически не существует.
- **ITL** есть не во всех версиях vLLM. При отсутствии строка помечается недоступной и
  **не заполняется** значением TPOT — величины считаются по-разному.

## Отклонения от проектных документов

Всё перечисленное сделано осознанно; менять обратно — ломать.

1. **Генератор — штатная Thread Group + Constant Throughput Timer**, а не `rpsThreadGroup()` из
   ARCHITECTURE §3.1 (Concurrency Thread Group + Throughput Shaping Timer). Смена по прямому
   указанию. Число потоков теперь фиксированное и считается из `ITERATION_SEC` и целевого RPM,
   обратной связи по фактическому темпу нет — темп задаётся тактом потока. Заодно исчез
   единственный в проекте пересчёт RPM в секундную частоту.
2. **Модель — на хосте, а не в `loadtest-net`.** `metrics-storage-stage.md` §2 фиксирует контракт
   «vLLM = `vllm:8000` в сети `loadtest-net`», а §9 держит это открытым вопросом. Фактически
   модель разворачивается на том же хосте вне докера. Имя `vllm` сохранено, но резолвится через
   `extra_hosts: host-gateway` — см. «Где живёт модель». Ценой двух строк в compose адрес во всех
   остальных местах остался прежним.
3. **`step` даёт секцию на каждую ступень и сводную таблицу.** В документах окно Hold описано в
   единственном числе. Один отчёт на шесть ступеней сделал бы режим бесполезным.
4. **`request.responseTimeoutSec` — 600, а не 180.** 180 с меньше `ITERATION_SEC` (300 с):
   запросы обрывались бы по таймауту и попадали в статистику как ошибки, роняя одновременно
   error rate и фактический RPM. Конфигурация с таким значением теперь не проходит валидацию.
5. **Добавлен `vm.settleSec` (35 с).** VictoriaMetrics по умолчанию не отдаёт данные за последние
   30 с (`-search.latencyOffset`), vmagent досылает последний скрейп не мгновенно. Без паузы
   хвост окна удержания оказался бы пустым, а отчёт об этом не сообщил бы.
6. **Добавлены `Generation Throughput Avg/Max`.** В оценку не входят, только в отчёт.
7. **Окна ступеней отсчитываются от старта первого запроса** (минимум `timeStamp` в `results.jtl`),
   а не от момента вызова `plan.run()`: между ними проходит построение и клонирование дерева
   плана, и на коротком разгоне смещение заметно.
8. **Разгон ступени поднимается до кратного такту потока** (300 с -> 375 с на штатном профиле).
   Иначе Constant Throughput Timer оставляет внутри окна измерения провал без запросов — см.
   «Почему разгон кратен такту». Прогон от этого длиннее заданного; стенд сообщает об этом
   при старте.
9. **E2E latency считается по успешным запросам.** Оборванный по таймауту запрос дал бы не время
   отклика модели, а значение `request.responseTimeoutSec`.
10. **Лимит пула HTTP-соединений не настраивается.** ARCHITECTURE §3.3 предполагает, что пул может
   стать скрытым потолком concurrency. Для реализации HttpClient4 в JMeter это не так: менеджер
   соединений создаётся per-thread (`HTTPHC4Impl.HTTPCLIENTS_CACHE_PER_THREAD_AND_HTTPCLIENTKEY`),
   общего потолка нет.

## Разработка

```bash
docker run --rm -v "$PWD":/build -v "$HOME/.m2":/root/.m2 -w /build maven:3.9-eclipse-temurin-21 mvn -B test
```

Юнит-тесты покрывают разбор профиля, расчёт потоков, датасет, тело запроса, фильтрацию по окну и
перцентили, каждое правило штрафа на граничных значениях, наложение `LT_*` и накопление ошибок
валидации, разрешение имён метрик и формат отчёта.
